# Assignment 2 build plan

Multi-agent briefing desk over Python docs and PEPs. A supervisor LangGraph routes each question to specialist agents, retrieves grounded passages from Chroma, queries a PEP table in SQLite, reads a small source bundle, and searches the live web through Tavily. FastAPI streams the answer, the route, the trace, and the citations to one vanilla HTML page on Cloud Run.

Work the phases in order. Each phase has a check you can run before starting the next one.

## Locked decisions

| Decision | Choice | Why |
|---|---|---|
| Product | Chat that answers questions about Python docs, PEPs, a PEP table, and a small source bundle | A grader can check the citation against a public document |
| Orchestration | LangGraph supervisor | Full credit. Hierarchical adds failure modes without raising the grade ceiling |
| Agents | Research, Data, Code, Summary | Supervisor does not count toward the three required specialists |
| Vector store | Chroma, embedded, index baked into the image | Same retrieval path locally and on Cloud Run |
| Live web | Tavily Remote MCP, shared by Research and Summary | Satisfies real-time knowledge and the MCP tool-sharing criterion |
| Providers | OpenAI `gpt-6.1-sol` for synthesis, summary, and code. Google `gemini-3.8-flash` for planning, query rewrite, and short lookups | Two companies. Ordinary questions hit both, because planning is cheap and synthesis is capable. GPT 6.1 Sol tool calls use the Responses API |
| Embeddings | OpenAI `text-embedding-3-small` | Same OpenAI key as GPT 6.1 Sol. Does not count as a second generation provider |
| Frontend | One HTML file, vanilla JS, `fetch` stream reader | No frontend framework, no `node_modules` in the image |
| Conversation state | Browser sends prior turns with each request | Server stays stateless. No Firestore unless you later promise sessions that survive refresh |
| Deployment | Cloud Run, timeout 300s, non-root container, `PORT` from the environment | Localhost-only submissions get no deployment credit |

Pinned ids, checked against the provider docs on 24 Oct 2026: `gpt-6.1-sol` and `gemini-3.8-flash`. Standard GPT 6.1 Sol prices are $2 per million input tokens and $10 per million output tokens. Do not use Ultrafast mode. It is several times more expensive and is not needed for the cost route.

## Phase 1 — Corpus and Chroma index

1. Download a real corpus, not a handful of files. Target 30 or more documents and thousands of chunks. Use CPython’s documentation (the `library/` and `reference/` or `tutorial/` HTML or the docs repo sources) plus PEP texts from the PEPs repository.
2. Record the snapshot date in `docs/architecture.md`. Questions about PEPs accepted after that date are the live-web demo.
3. Parse each document into sections. Keep metadata: `doc_id`, `title`, `section`, `source_url`, `chunk_id`.
4. Split on markdown or HTML headings where they exist. Otherwise use a recursive splitter at about 1,000 characters with about 200 characters of overlap.
5. Embed with `text-embedding-3-small` and write a persistent Chroma collection named `corpus`. Store the chunk text and metadata. Use stable chunk ids so re-running ingest updates instead of duplicating.
6. Write `ingest/build_index.py` so ingestion is a script, not something that runs on container startup.
7. Smoke-test retrieval with three questions whose answers you can point at: one definition, one that needs two chunks, one that should miss the index.

**Done when:** `collection.count()` is in the thousands, and a manual query returns the passage you expected with its `chunk_id` and source.

## Phase 2 — SQLite table and code bundle

1. Build `data/peps.sqlite` from the PEP index. Columns that support real questions: `number`, `title`, `status`, `type`, `created`, `python_version`, `author`. One table is enough if the questions are real.
2. Implement a read-only SQL tool. It accepts a single `SELECT`, rejects anything else, uses a row limit, and returns rows plus the SQL text. The tool reads `SQLITE_PATH`.
3. Vendor a small source tree into `code_bundle/`. Prefer modules you can legally redistribute (a few CPython `Lib/` modules with their license notice, or a short set of scripts you write that implement PEP-related helpers). The code agent must have files to open.
4. Implement `search_code(query)` and `read_file(path, start, end)`. Resolve paths inside `code_bundle/` and refuse paths that escape it.

**Done when:** the SQL tool answers “how many PEPs have status Final” with a count you verified by hand, and `read_file` returns a known line range.

## Phase 3 — State, prompts, and the supervisor graph

State fields the trace will print:

- `user_query`
- `history` (prior turns from the browser)
- `plan`: list of `{id, agent, reason, depends_on, status}`
- `route_log`: list of `{agent, provider, model, dimension, reason, fallback}`
- `agent_outputs`: map of step id to text
- `citations`: list of `{chunk_id, source, title, section, score, excerpt}`
- `errors`: list of `{agent, message, recovered}`
- `trace`: list of `{node, event, detail, ts}`
- `final_answer`

Agent boundaries:

| Agent | Tools nobody else has | Prompt job |
|---|---|---|
| Research | Chroma retriever, Tavily search | Answer from retrieved chunks. Cite `chunk_id`. Call web search only when the corpus has no supporting passage or the question is about events after the snapshot date |
| Data | SQLite read-only tool | Answer only from query results. Put the SQL in the tool result |
| Code | `search_code`, `read_file` | Explain or write code against `code_bundle/`. Cite `path:line` |
| Summary | Tavily extract | Merge prior outputs. Keep every citation. Extract a URL only when Research returned one to verify |

1. Put each system prompt in `app/prompts.py`. Do not reuse one prompt with a different name.
2. Add a plan node. It calls the cheap model and returns structured JSON: which agents to run, in what order, and why. Validate the JSON. If parsing fails, fall back to a single Research step and log that fallback in `trace`.
3. Add a supervisor node. It reads `plan` and marks the next step whose dependencies are `done` or `failed`. It does not inspect keywords in Python.
4. Add one node per agent. Each node appends trace events on entry and exit.
5. Compile a LangGraph `StateGraph`: start at plan, then supervisor, conditional edges to the four workers, every worker returns to the supervisor, supervisor routes to summary when every planned step is finished, summary ends the graph.
6. Run the graph once in a script for each starter question and print `plan`, `trace`, and `final_answer`.

Starter questions:

- What does PEP 8 say about imports?
- How many PEPs in the table have status Final?
- Show the function at a path you know exists in `code_bundle/` and explain it.
- What PEPs were accepted after the corpus snapshot date?
- Combine a PEP 8 rule with the count of accepted PEPs of type “Process” and a one-paragraph summary.

**Done when:** the five questions produce five different plans, workers return to the supervisor, and the graph reaches a final answer.

## Phase 4 — Provider routing

1. Implement `choose_provider(task)` in `app/routing.py`.
   - Cost route: planning, query rewrite, and short answers where a chunk already contains the fact. Use `gemini-3.8-flash`.
   - Capability route: multi-document synthesis, summary, and code. Use `gpt-6.1-sol` through the Responses API when the call includes tools.
   - The plan step sets `complexity` to `low` or `high`. The router reads that field. It does not always return the same provider.
2. Append every decision to `route_log` with `dimension` and a one-sentence `reason`.
3. On provider error, retry that step once on the other provider. Set `fallback: true` and `recovered: true`. If the retry fails, mark the step failed and continue the graph.
4. Re-run the five starter questions. Save the route log.

**Done when:** a normal session shows both providers, each reason is readable without opening source code, and a forced failure of the strong model still returns an answer from the cheap model.

## Phase 5 — Tavily shared by two agents

1. Connect with `langchain-mcp-adapters` to `https://mcp.tavily.com/mcp/?tavilyApiKey=<key>` over Streamable HTTP. Pass the key as the query parameter. Do not put it in the body.
2. Give Research the search tool. Give Summary the extract tool. Both tools come from that one MCP server.
3. Teach Research to call search when retrieval scores are weak or the question asks for something newer than the snapshot. Teach Summary to call extract only on URLs Research already returned.
4. Run the “after the snapshot” question and one mixed question.

**Done when:** the trace for one deployed-style query shows Research calling Tavily search and Summary calling Tavily extract, with different arguments.

## Phase 6 — Failure handling

1. Wrap each worker body in `try/except`. On exception, append to `errors`, set that step’s status to `failed`, append a trace event, and return to the supervisor.
2. The supervisor skips dependents that cannot run, sends completed work to Summary, and Summary states what is missing.
3. Add a graph-level guard so an unexpected exception becomes an error payload instead of a crashed process.
4. Unit-test this by raising inside the Data node once.

**Done when:** a broken Data step still produces a Summary answer, and `errors` names the agent and says the failure was recovered.

## Phase 7 — FastAPI and SSE

1. `POST /api/chat` accepts `{query, history}`. `history` is a list of `{role, content}` from the browser. The server does not store it.
2. Stream Server-Sent Events from that POST response. The browser will use `fetch` and a stream reader, not `EventSource`.
3. Emit events as the graph runs, not after it finishes. Use a callback or stream writer from each node.
   - `trace` — node, event, detail
   - `route` — agent, provider, model, dimension, reason
   - `citation` — chunk id, source, title, section, score, excerpt
   - `token` — answer text pieces from Summary
   - `error` — agent, message, recovered
   - `done` — empty payload
4. Write a `: ping` comment as soon as the handler starts, before the first model call, so Cloud Run and the browser see bytes during cold start.
5. `GET /health` returns `{ok, chroma_count, providers_configured}` and never returns key values.
6. Serve `static/` at `/`.

**Done when:** `curl` against `/api/chat` shows `trace` and `route` lines before the full answer, and `/health` reports a non-zero chunk count.

## Phase 8 — Frontend

One page, no build step.

1. Layout: query box and streaming transcript on the left. Live trace on the right. Starter-question buttons that fill the box with the five questions from Phase 3.
2. Parse SSE frames. Append tokens to the current assistant message. Append trace rows as they arrive. Render a route line under the answer: agent, provider, model, reason.
3. Render citation chips. Clicking a chip shows chunk id, title, section, score, and excerpt.
4. Send `history` from the messages already on the page so a follow-up in the same tab has context. Do not claim that a refresh keeps server-side memory.
5. Show an error row in the trace when an `error` event arrives, and still show whatever answer streamed.

**Done when:** you can ask a corpus question in the browser, see tokens arrive before the answer is finished, read why a provider was chosen, and open a citation to a real chunk id.

## Phase 9 — RAGAS and measurements

1. Commit `eval/questions.json` with about 20 fixed questions. For each, store the question, the expected source ids or a short reference answer, and whether the corpus should contain the answer.
2. Run RAGAS for faithfulness, answer relevance, context precision, and context recall. Write the numbers into `docs/evaluation.md` with the date you ran them.
3. Time retrieval, LLM calls, and total wall clock. Record time-to-first-token warm, and one cold-start figure after the Cloud Run deploy in Phase 11. Warm numbers are the ones you present as representative. Note cold start separately.
4. Estimate cost per query from token counts and the providers’ published prices. Compare the cheap model and the strong model on a few of the same questions: quality notes, latency, and estimated cost.

**Done when:** `docs/evaluation.md` contains four concrete RAGAS numbers, a latency split, a cold-versus-warm note, and a provider comparison. Partial credit on RAG is what you get if this file has no numbers.

## Phase 11 — Container and Cloud Run

1. Dockerfile, Python 3.13-slim, multi-stage. Install dependencies into a path the runtime user can read. The syllabus sketch copies into `/root/.local` and then switches to `appuser`; that user cannot read `/root/.local`. Install to `/usr/local` or copy the environment into `/home/appuser` and `chown` it.
2. Create `appuser`, run as that user, copy the app, the baked `chroma_index/`, `data/peps.sqlite`, `code_bundle/`, and `static/`.
3. Start uvicorn on `0.0.0.0` and port `$PORT` (default 8080). Do not call a provider or re-embed at import.
4. Enable `run.googleapis.com`, `cloudbuild.googleapis.com`, and `artifactregistry.googleapis.com`.
5. Deploy with timeout 300, memory 2Gi, cpu 1, concurrency 10, min-instances 0, max-instances 3, allow unauthenticated. Pass secrets as Cloud Run env vars, not build args baked into the image.
6. After the URL prints, in a browser:
   - Cold-load the URL and confirm the first request streams instead of failing.
   - Ask a corpus question and open a citation.
   - Ask a question that is only answerable from the web after the snapshot date.
   - Ask a SQL question and a code question.
   - Ask something outside the domain and confirm a normal answer and a clean trace.
   - Ask a follow-up in the same page and confirm `history` was sent.
   - Note warm TTFT and one cold TTFT in `docs/evaluation.md`.

**Done when:** the public URL answers those queries after a cold start, `/health` is green, and the trace shows agent, provider, and reason.
